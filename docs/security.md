# Security model

## Connectivity

- Agents only ever make **outbound** connections to the server
  (`wss://` control channel + `https://` data plane). No listening ports,
  no VPN, no firewall changes on clients.
- The server exposes exactly one TCP port (default 8443) for everything:
  GUI, API and agents.

## Server authenticity (why self-signed is safe here)

The server generates a self-signed TLS certificate on first start. Agents
do **not** use the system CA store; they verify the certificate's SHA-256
fingerprint, pinned at enrollment:

1. The enrollment command generated in the GUI includes the fingerprint.
2. `backup-agent enroll --fingerprint …` refuses to talk to a server whose
   certificate doesn't match (with `--fingerprint` omitted it's
   trust-on-first-use, printing the fingerprint for manual verification).
3. The pinned fingerprint is stored in `creds.json` and enforced on every
   subsequent connection.

A man-in-the-middle therefore cannot impersonate the server after (or
during, when the fingerprint is passed) enrollment. To use a CA-issued
certificate instead, set `CB_TLS_CERT`/`CB_TLS_KEY` — but note that
replacing the certificate later changes the fingerprint and requires
re-enrolling agents.

## Client authentication

- Enrollment requires a **one-time token** (24 h validity, single use)
  generated by an admin in the GUI.
- At enrollment the agent receives a permanent agent ID + 256-bit random
  secret; both are stored hashed (SHA-256) server-side and sent on every
  request. An agent can only touch its own runs, snapshots and manifests.

## Admin authentication

- Username/password (bcrypt), session cookie (`HttpOnly`, `Secure`,
  `SameSite=Lax`), 7-day expiry.
- State-changing API calls additionally require the `X-Requested-With`
  header, which cross-site form posts cannot set (CSRF defence in depth).
- First run: the `/setup` page creates the admin account; it is disabled
  as soon as one user exists.

## Data integrity

- Every file blob is verified against its SHA-256 on **upload** (server
  decompresses and hashes before the blob becomes visible) and on
  **restore** (agent re-verifies after download).
- Manifests are committed only after all referenced blobs are stored;
  the agent double-checks and excludes files whose data could not be made
  consistent (reported as "partial" runs).
- Garbage collection never removes blobs referenced by any manifest, holds
  a commit lock, and skips blobs younger than 24 h (protects in-flight
  backups).

## Current limitations (see roadmap)

- Backups are compressed but **not encrypted at rest** — anyone with
  filesystem access to the server's storage can read backed-up data.
  Client-side encryption is a planned enhancement; meanwhile treat the
  backup server as sensitive infrastructure and encrypt the disk.
- No per-admin roles; a single admin level.
- Locked/open files on Windows are skipped (and reported), not
  snapshotted via VSS yet.
